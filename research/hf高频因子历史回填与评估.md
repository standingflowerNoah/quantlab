### 3.3 关键观察

1. **补齐历史是"质变"不是"量变"**：2025-2026 两年窗口下这批因子 FDR 几乎全不显著；
   五年窗口下 16/21 显著、**19/21 年度方向零反号**。样本长度本身改变了结论强度。
2. **残差 IC 保持率中位 0.99**：对 `size + amihud_20`（生产组合两因子）正交化后几乎不缩水
   → 这批因子与生产组合**信息正交**，组合分散价值真实存在。
   唯一例外 `hf_amtrange_20`（残差 -0.0025，保持率 ≈0）——**已被生产因子完全覆盖，应淘汰**。
3. **hf_amihud_20（分钟版）**：IC20 +0.1012 是全表最强；对生产用日线 `amihud_20` 正交化后
   残差 IC 仍有 +0.0915 → 分钟口径比日线口径信息量明显更高，**有升级替换价值**。
4. **半衰期普遍 >120 日**（测程内未衰减过半）→ 慢衰减配置型信号，月频/季频换手即可，
   与"高频因子低频化"范式一致；不会像日内信号那样被换手成本吞噬。
5. **hf_dsem_20 方向为正**（+0.089）：下行方差占比越高未来收益越高——与"低波动异象"
   族的反向逻辑自洽（下行风险占比高=被错杀）。

## 五、附：过程中的坑（工程）

1. **quant.duckdb 写锁**：`compute_factor`/`audit_factor` 需要 Store，而另一会话的
   `backfill_metric_daily` 长期占用写锁 → 22 个因子全部失败。
   解法：hf 因子是 SqlFactor 且只读 minute_feat+kline_daily（**两张表都是 Parquet**），
   自建内存 DuckDB 注册视图即可完整复算，绕开主库。
2. **maybe_audit 会跳过**：补齐 2022-2024 后 `latest_date` 仍是 2026-09-10（未变），
   `maybe_audit` 判"数据未变"直接 return → 审计 JSON 不会刷新。
   必须显式 `audit_factor(name, deep=True, force=True)`。
   ⚠️ 本轮审计因写锁未完成，**audit JSON 的 IC 仍停留在 2025-2026 窗口**，待锁释放后补跑。
3. **重试条件漏匹配**：DuckDB 锁冲突文案是"另一个程序**正在使用**此文件"，
   原重试逻辑只匹配"lock/Conflicting/**正在写入**" → 未触发重试。
4. **分段重算的浮点噪声**：按月分块 vs 整年一次，求和顺序不同 → 1e-17 级差异（无害）；
   `hi_pos/lo_pos` 在一字板退化日（high==low 全日）出现 arg_max 并列歧义（0.53% 行）。
5. **进程静默死亡**：本轮 4 次进程被无声回收（25-40 分钟一次）。
   `nohup+disown` 在本机不可靠；托管后台 17h 稳定 → **长跑作业一律走托管后台**，
   且管线每一步都要可断点续跑（本次已实现：minute_feat 按年跳过、因子 append 幂等）。
