# Tick 数据源盘点与 Tick 数据库建设方向评估

- 评估日期：2026-09-06
- 评估范围：A股 / 国内期货 / 加密货币 / 美股的开源与低成本 tick 数据源；tick 规模存储技术选型
- 结论性质：数据驱动，含负面判断；所有关键数字标注来源与时点

---

## 0. 结论先行（TL;DR）

1. **A股逐笔级（L2）历史数据不存在开源渠道**——这是交易所授权制的商业数据（上交所官方报价 12 万元/年，2020 版产品说明书口径；经港渠道约 $6,000/3 个月，2026-08 官网口径）。市面上所有"A股逐笔历史"要么是商业转售，要么是机构/个人的私下录制件，没有合法开源全集。
2. **真正开源/免费可得的 tick 只有三类**：
   - **加密货币**：Binance Vision 全品种 aggTrades/trades 免费、全历史、带校验和（2017 年起）——全球最干净的免费 tick 源；
   - **国内期货**：天勤 TqSdk 免费提供全市场合约从上市起的 tick（宣传口径约 10 年深度，需实测）；
   - **自录**：QMT/miniQMT 实时订阅录制（3 秒快照免费；L2 逐笔需 Level-2 权限）。

   另有 **free-stockdb**（GitHub hello245m/free-stockdb，约 2.1k★，MIT）：把 2000 年起全市场日线 + 1/5/15/30 分钟线（约 1.1 亿条，20GB Zstd）打包本地化分发——**分钟线历史回补价值大**；但其"tick 级数据"在 README 中仅有"按需"二字，无覆盖范围/粒度/深度/样例任何细节，**不能当作 tick 数据源**，且数据授权链条不透明，详见 2.4 节。
3. **A股个人研究的性价比起点是 3 秒快照，不是逐笔**。QMT 的 `get_full_tick`/`period='tick'` 本质是 3 秒快照（券商口径：Level-1 快照由交易所每 3 秒推送一次），免费、门槛为券商账户日均资产 10 万元（miniQMT，各券商有差异）。逐笔数据只能从开通之日起自己积累，**历史无法回补**——这是硬约束。
4. **存储选型：Phase 1 不换栈**。现有 DuckDB + Parquet 数据湖完全扛得住 3 秒快照层（全市场一年约 50-100 GB Parquet）；数据量到 TB 级或需要交互式 ASOF 查询时再引入 QuestDB/ClickHouse 做加速层。**Parquet 是开放格式，先落地永远不会被锁死**。
5. **对当前 Alpha191 日频主线，tick 库边际收益短期不高**；真正的受益者是分钟级/日内微观结构因子。建议先建"1 分钟 + 3 秒快照"两层，与现有 lake 无缝衔接，再按研究需要向上加逐笔层。1 分钟层的历史回补优先走 free-stockdb（对账后转 Parquet），QMT 作每日增量源。

## 2. A 股数据源盘点（按渠道）

### 2.1 官方交易所渠道（一手来源，商业定价）

| 项目 | 内容 | 来源与时点 |
|---|---|---|
| 上交所 Level-2 行情历史数据 | 12 万元/年（含快照+逐笔成交+逐笔委托+K线） | 上交所信息网络公司《历史数据产品说明书》v1.0.0，2020-02-19 |
| 上交所 L2 逐笔合并数据（新格式，含委托队列） | $6,000/3 个月 ≈ $24,000/年 | 中国投资信息服务（香港）官网，2026-08 更新页面 |
| 中金所 L2 快照历史 | $1,200/3 个月（近三年） | 同上 |
| 交付方式 | 云平台保留近 2 周 / 5GB-256GB 用 U 盘 / 更大用移动硬盘 | 同上 |

**判断**：个人研究预算下不值。这套价格面向机构。除非商业化且高频因子成为核心收入，否则不建议采购。

### 2.2 券商量化终端（个人性价比最优）

**QMT / miniQMT（迅投）**

| 维度 | 事实 | 来源 |
|---|---|---|
| 开通门槛 | miniQMT：近 20 交易日日均资产 ≥10 万元（国金等）；完整版 30-50 万 | 券商宣传页 2026，各券商有差异 |
| 费用 | 软件免费、无数据服务费；唯一成本是交易佣金 | 同上（注意此类页面带营销性质，签约前以券商官方协议为准） |
| tick 粒度 | 默认 tick = **3 秒快照**（Level-1，交易所每 3 秒推送；有变动才推，活跃股约 3 秒/次） | 券商从业答复 2026-08-26，需实测核实 |
| L2 数据类型 | `l2quote`（十档快照）、`l2order`（逐笔委托）、`l2transaction`（逐笔成交）、`l2orderqueue`（买卖一前 50 笔队列）、`l2thousand`（千档） | 迅投文档/券商答复，2026 |
| L2 权限 | 部分券商需单独开通 Level-2（有的新户活动免费，有的收费） | 券商宣传页，签约前核实 |
| 历史深度 | 日/分钟线多年；tick（3 秒快照）历史多年可回补；L2 逐笔历史深度有限（主要是实时订阅+本地录制） | 需实测确认 |
| 沪深差异 | 沪市 L2 快照 3 秒基准；深市 L2 逐笔为事件驱动（有成交/新委托即推） | 券商从业答复 2026-08 |

**关键准确性提醒**：营销页面宣称"免费 Level-2 十档逐笔行情永久开放"与实际体验常有不符——**L2 逐笔在 QMT 里主要作为实时订阅流存在，历史逐笔的下载深度是有限的**。落地前务必实测：`xtdata.download_history_data(period='tick')` 能回补多久、`l2transaction` 订阅能否落盘。

### 2.3 开源 Python 数据库（免费层能力边界）

| 库 | tick 能力 | 限制 | 来源 |
|---|---|---|---|
| AkShare (16.3k★, MIT) | 无历史分笔；当日分笔走腾讯源 | 爬虫本质，东财接口 2024-08 曾连续 3 天中断；实时延迟 p50 约 5.8s | 财联社 2025 + atick.ai 实测 2024-11 |
| Tushare Pro | 分钟线 2000 积分；tick 级数据 5000+ 积分 | 无 A 股全市场逐笔历史批量接口；积分制（注册 120 分起） | tushare.pro 官方文档 |
| efinance | 1 分钟仅当日，5 分钟近 2 个月 | 历史深度硬伤 | 财联社 2025 |
| Baostock | 5 分钟 K 线（2015 年起） | 无 tick；无实时 | 官方文档 |
| qlib (37.5k★) | 日线 + 分钟（官网下载包） | 无 tick | 微软官方 |

### 2.4 free-stockdb（开源本地数据引擎，2026-09-06 复核）

GitHub `hello245m/free-stockdb`，MIT（代码），C++17 + LevelDB 本地引擎 + Rust 指标计算，约 2.1k★，2026-05 创建、2026-08-27 仍在更新，支持 Windows/macOS/Linux。

| 维度 | 事实（README 原文口径） | 评估 |
|---|---|---|
| 数据覆盖 | 日/周/月线 + 1/5/15/30 分钟线，2000 年至今，7000+ 股票/ETF，约 1.1 亿条；含复权因子、申万一二三级 + 1200 概念板块 | **分钟线历史回补的真实价值点**：比 Tushare 积分制/efinance 近端限制/QMT 逐股回补都快得多 |
| 存储与体量 | Zstd 压缩，全量分钟线约 20GB；本地服务 127.0.0.1:7899 | 单机友好，体量与"1 分钟线 26 年"的宣称自洽（约 1.1 亿条 × 列存压缩合理） |
| tick 级 | README 仅写 "tick级数据(按需)"，sync_url.txt 支持 `ticks_data` 数据源挂载 | **无任何兑现细节**：无覆盖范围、无历史深度、无粒度定义（快照还是逐笔不明）、无样例。推荐配置 20GB 也装不下正经 tick 集（全市场快照一年即 50-100GB）。**评估结论：不能作为 tick 来源，只是"引擎支持挂载 tick 数据"的架构声明** |
| 数据分发 | 数据不在 repo（Release 仅约 3MB，data/ 空），首次从作者镜像/网盘同步；第三方核验 2026-07-26 发现镜像 manifest.txt 曾 404 | 单点依赖作者服务器；数据量与时效无法独立复核 |
| 数据来源授权 | README 免责声明原话："数据版权、使用授权和再分发条件由各数据源及其权利人决定；使用者应自行确认数据源条款" | **来源未披露**，授权链条不透明；26 年全市场分钟数据大概率采集自东财/通达信等免费行情，属灰色地带。个人研究自用风险低；**不可作为商业化依赖，不可再分发** |
| 与本项目集成 | `get_data()` 可返回 DataFrame，可导出转 Parquet | 正确用法：**抽取工具而非 source of truth**——同步后导出 → 抽样对账（Tushare/AkShare/QMT 交叉验证）→ 转 Parquet 入 `lake/clean/`，之后研究只依赖自有 lake |
| 定位 | 数据工程自动化（同步/清洗/复权/板块映射）+ 本地查询引擎 | 工程思路值得借鉴；对我们是"分钟线层加速器"，不是 tick 库方案 |

**判断**：值得在 Phase 1 用它做分钟线历史回补（省 3-5 天逐股下载），但必须过三关：①数据抽样对账（价格/成交量/复权因子与 Tushare、QMT 交叉验证）；②确认导出能力与稳定性；③只作采集通道，Parquet lake 仍是唯一事实源。tick 层不要对它抱预期。

### 2.5 商业 API（对比参考）

iTick、Alltick、TickDB 等新兴 API：加密货币支持好；**A股 tick 级普遍不支持或不稳定**（TickDB 明确 A 股无逐笔）。付费源里沧海数据、理杏仁、EODHD 覆盖分钟级为主。来源：atick.ai 对比文 2026 / 财联社 2025。非一手来源，采购前需逐家核实。

## 4. 数据规模估算（决定存储选型的关键输入）

### 4.1 A 股逐笔规模（官方口径 + 估算）

| 指标 | 数值 | 口径与来源 |
|---|---|---|
| 深市股票成交笔数 | 154.55 亿笔 / 220 交易日 = **日均 7,025 万笔** | 深交所官方月报，2025 年 1-11 月（一手来源） |
| 全 A 逐笔成交（估算） | **日均 1-1.5 亿条**（沪市约为深市 60-70%） | 估算：基于深市官方数 + 2026Q1 日均成交额 2.6 万亿元（新浪财经/Wind 口径 2026-04，交投活跃期偏高） |
| 上市公司数 | 5,496 家（2026Q1 末） | 新浪财经 2026-04 |
| L2 全量日增量 | **30-45 GB/天**（快照+逐笔成交+逐笔委托+队列，未压缩口径），历史 10TB 级 | 腾讯云开发者文章 2026-03（非一手，量级与下述估算交叉验证一致） |

### 4.2 存储需求估算（列存 Parquet/zstd 压缩后，经验值估算）

| 数据层 | 行数/天 | 压缩后/天 | 一年（250 交易日） | 说明 |
|---|---|---|---|---|
| 3 秒快照（全市场，20 列） | ~2,640 万行 | 200-400 MB | **50-100 GB** | 5500 股 × 4,800 个 3 秒槽位 |
| 逐笔成交（沪深） | 1-1.5 亿行 | 2-3.5 GB | **500-900 GB** | 每行约 20-25 字节压缩 |
| 逐笔委托（含撤单，估算为成交 2-4 倍） | 3-5 亿行 | 6-12 GB | **1.5-3 TB** | 沪深结构不同需分表 |
| L2 全量合计 | — | 30-45 GB（未压缩）→ 8-15 GB（压缩） | **~10 TB 级** | 与 4.1 交叉验证一致 ✓ |

**结论**：3 秒快照层在现有 DuckDB+Parquet 栈的舒适区内；逐笔层一年 TB 级，单机仍可管理（一块 4TB NVMe 即可），但要认真设计分区与压缩；L2 全量（含委托队列）才真正需要专用时序库。

### 4.3 参考量：加密货币

BTCUSDT 一天 aggTrades 约 100-300 万行（随行情波动），10 个主流交易对一年 Parquet 约 50-150 GB——作为样板库毫无压力。

## 5. 存储技术选型对比

### 5.1 第三方实测数据（同机对比，473 MB 1 分钟 K 线数据集）

| 数据库 | 写入耗时 | 磁盘占用 | 查询耗时（5min 聚合） |
|---|---|---|---|
| DolphinDB (TSDB) | 39.8 s | **265 MB** | 7.7 s |
| QuestDB | **13.3 s** | 560 MB | **7.6 s** |
| ArcticDB | 15.8 s | 272 MB | 12.7 s |
| TDengine | 23.3 s | 626 MB | 15.9 s |
| TimescaleDB | 229.1 s | 813 MB | 23.7 s |

来源：GitHub edwardzhu/tsdb-analysis 实测（社区项目，数据集为 Binance 1m 数据，非官方 benchmark，量级参考）。
另：QuestDB 官方 2025 benchmark 宣称 1B ticks 写入 9.5M rows/s、存储 55 GB（厂商口径，需核实）；某算法交易团队实测 ClickHouse 单节点加载 3,500 万笔交易 + 7.19 亿笔报价速度超 1M rows/s、磁盘约为压缩源文件一半（腾讯云社区译文，2019，年代较早仅作量级参考）。

### 5.2 选型矩阵（结合本项目约束）

| 维度 | DuckDB+Parquet（现有栈） | QuestDB | ClickHouse | DolphinDB 社区版 | ArcticDB |
|---|---|---|---|---|---|
| 许可/成本 | MIT，免费 | Apache 2.0，免费 | Apache 2.0，免费 | 免费（**限 2 节点 × 2核8GB**；Pro 15,800 元/年） | Apache 2.0，免费 |
| 与现有 lake 兼容 | ★★★ 零成本（就是它） | ★★ 可直接读 Parquet | ★★ Parquet 引擎成熟 | ★ 需自建存储+专有语言 | ★ Python 原生但独立体系 |
| 写入模式 | 批式（适合盘后批量） | 实时 ILP 极强 | 批式强 | 批式+流式均强 | 批式 |
| ASOF JOIN | 1.x 已支持，够用 | 原生、最强 | 支持（语法繁琐） | 原生强 | 无（pandas 层做） |
| 运维成本 | 零（嵌入式） | 低（单二进制） | 中（配置项多） | 中（部署+学习 DolphinDB 脚本） | 低 |
| 单机数据量舒适区 | ~TB 级（快照层绰绰有余） | TB-PB | TB-PB | TB-PB（但社区版 8GB 内存卡脖子） | TB 级 |
| 生态风险 | 无（开放格式） | 低 | 低 | **中（商业公司，社区版随时可改政策）** | 低（MAN 维护） |

### 5.3 选型结论

- **Phase 1（快照+分钟层，<200 GB）：不换栈。** DuckDB + Parquet 按日分区，与现有 `data/lake` 同构，单写者串行调度直接复用。查询性能对研究负载（每天几百次全表/分区扫描聚合）完全够用。
- **Phase 2（逐笔层，TB 级，需要 ASOF/交互式查询）：引入 QuestDB 做热加速层。** 理由：开源 Apache 2.0、单机性能实测第一梯队、原生 ASOF JOIN、能直接读 Parquet（lake 仍是 source of truth）、单二进制运维成本最低。**不选 DolphinDB** 的原因：社区版 2核8GB 内存限制在逐笔层真实查询（多标的 ASOF join）下会撞墙，Pro 版 15,800 元/年不如把钱花在数据采购上；且专有脚本语言的学习成本对单人项目是纯负担。**不首选 ClickHouse** 的原因：分布式 OLAP 定位，个人单机场景优势发挥不出来，运维面大（对网络受限的 Docker 环境也不友好）。
- **任何阶段：Parquet 分区文件都是 source of truth**，数据库引擎只是可替换的查询加速层。这样 QuestDB 出问题、或未来换 ClickHouse/DuckDB 新版本，数据零迁移。

## 7. 分阶段落地路线

**Phase 0：样板验证（本周可做，零成本）**

## 8. 风险与诚实判断

1. **A股逐笔历史无法回补是结构性约束**。想复现 2015-2025 全历史逐笔因子，个人层面不现实。若有此需求，唯一务实路径是商业采购（数万元级），且需评估数据合规链路。**建议研究设计上避开依赖全历史逐笔的题目，转向"快照级可复现 + 逐笔级前瞻验证"的混合方案**。
2. **QMT 的免费承诺要打折听**。"免费 Level-2 永久开放"来自券商营销页；实测重点：L2 逐笔订阅稳定性、历史回补深度、非交易时段数据可用性。以实测为准，签约前不假设。
3. **3 秒快照的研究边界**：做不了真正的订单流/撤单分析（撤单只体现在快照的挂单量变化里），但覆盖绝大多数日内量价因子（含 Alpha191 的日内化变体）。这是"够用"与"完美"之间的务实落点。
4. **天勤免费 tick 的隐性限制**（并发、限速、生态绑定）未实测，Phase 1 验证。
5. **free-stockdb 的三重风险**：①数据来源未披露、授权链条不透明（README 自身免责条款要求使用者自行确认），个人研究自用风险低，**不可商业化依赖、不可再分发**；②个人项目单点——镜像曾 404（2026-07-26 第三方核验），断更即失效，所以必须导出 Parquet 归自有 lake，不留私有 LevelDB 单点；③宣传口径（"tick 级"）与兑现细节（无）之间的落差，README 的能力矩阵不能当数据清单读。
6. **合规红线**：QMT/天勤的数据授权均限于个人使用，禁止转售或公开分发；商业数据（若采购）同样有授权边界。建立 tick 库自用没问题，商业化要注意授权条款。
7. **DolphinDB 社区版政策风险**：商业公司免费政策可变（参考其 Pro 版定价策略的演进），核心数据资产放 Parquet 可对冲此风险。

### 10.2 实测修正前文判断

1. **镜像可用性**：curl 直接访问 manifest 返回 204（重定向到 workbuddy 站点后无内容），但**官方同步器可正常工作**（疑似 Cloudflare Worker 按客户端特征放行）。评估期镜像曾 404 的历史属实，单点风险仍在——但"导出 Parquet 归自有 lake"的架构已落地，断更只影响增量不影响存量。
2. **分钟数据真实覆盖：2025-01-02 起**（README 未明说）。首日 5,083 只，2026-09-04 达 7,198 个代码（含 ETF 等）。**"时间范围与日频对齐"只能对齐到 2025-01-02**——2022-2024 的分钟缺口无免费开源渠道可补（baostock 仅 5 分钟线且频率不一致），商业源是唯一选择。MINUTE_START 保持 2022-01-01 配置，未来数据源扩展时自动吃到更深历史。
3. **数据新鲜度**：分钟/日线均更新至最近交易日（2026-09-04），作者维护活跃。
4. **引擎工程质量（重要）**：C++ 引擎与 pyd SDK 存在三类实测 bug：
   - pyd 长连接在连续大查询下**响应队列串位**（A 股查询返回 B 股数据，2026-09-06 压测复现：000002 的查询返回 601318 的 97,839 行）；
   - 部分异常静默返回错误字符串 `'Missing required parameters'` 而非抛异常；
   - SDK `get_data`/mget pipeline 对分钟范围查询静默返回空。
   **对策（已实施）**：生产路径全部改走 **HTTP API（每请求独立连接 + msgpack 解码）**，压测 18/18 零失败；每次查询做**响应身份校验**（行内 code 必须与请求一致，错数据宁可失败不落库）。
5. **成交量单位实测**：kline_daily.vol（tdx 源）为**股**而非注释所写"手"（amount/均价=vol 交叉验证，fsdb 分钟求和与日线吻合到个位数）。kline_1min.vol 直接存股，与日线同单位；tdx_source.py 注释已修正。

### 10.4 增量路径加固与端到端验证（2026-09-07 00:06）

上线前自查 + 端到端测试（`minute-update` 真实每日路径）暴露三个缺陷，当晚全部修复：

**① 增量防双写（minute.py）**：lookback 回看窗口（5 天）与 part-b 回补存量重叠是常态 → 首次增量会双写 ~520 万行。修复：写入前 anti-join part-b 已存在 (code, datetime) 键（merge + left_only）；part-d 之间仍靠同名覆盖幂等（盘中补跑语义）。**坑：DuckDB `.df()` 返回 datetime64[us]，与拉取侧 ns 的 merge 键 dtype 不一致会静默零命中**——必须 `astype("datetime64[ns]")` 归一化。端到端实测：5,554 只 × 5 天窗口 626 万条存量键全量剔除，**入湖 0 行、0 个 part-d 文件、湖行数不变（519,316,060）**。

**② 同步器挂起（fsdb_source.py）**：`数据更新.exe --sync` 为 GUI 程序，无增量日 ~10s 完成全部工作（双库清单零差异、零 .part）后**不退出**（零 CPU/零 TCP/零写入静默存活），`subprocess.run` 阻塞到 4h 超时。诊断三件套：CPU 累计值 + TCP 连接 + 目标目录最近写入。修复：`_watch_sync` 空闲看门狗（Popen + 15s 轮询 data/data1 双库目录快照，宽限 90s + 空闲 240s 即回收；已完成纯闲置杀之无损，网络停滞 .part 断点续传）。镜像实际落两个 LevelDB 目录：data（主库 22GB）+ data1（1.8GB），完成判定与体量统计均已改双库。无增量日同步开销 ~5.5 分钟。

**③ wm_full 死分支（minute.py）**：watermarks 表列为 DATE（全域共享），`_refresh_watermark` 存 `.date()` 截断时间 → "同日且 hour≥15" 永远 False → 周末/节假日每次跑增量全窗口冗余拉取。修复：完整性判定改为 `_scan_lake_max_datetime()` 直扫湖（read_parquet MAX(datetime)，行组统计量 0.7s，绕开视图/镜像/锁）；盘中场景（last_bar 14:xx）正确判 False 不漏收盘段。

**北交所分钟覆盖边界（重要数据事实）**：920 段 341 只中日频正常交易，但 fsdb 分钟数据**287 只止于 2026-01-20**（此前有数据）、54 只全程无数据——**时变缺口**而非二值覆盖。连同沪深次新 29 只、个别异常 4 只，共 374 只"日频有/分钟无"，每日窗口复查成本 ~30s，维持不加前缀过滤的自愈设计（fsdb 若恢复收录自动流入）。

### 10.5 运行手册

```bash
# 首次全量回补（断点续跑，~2.1s/只 × 5,554 只 ≈ 3.2 小时）
python cli.py data minute-init

# 日常增量（已接入 update_all，亦可单独跑）
python cli.py data minute-update

# 覆盖统计 / 对账日线
python cli.py data minute-status
python cli.py data minute-validate --sample 50
```

依赖：venv 需 `requests`、`msgpack`（已装）。stockdb.exe 常驻后台（127.0.0.1:7899），同步期间自动停起。
