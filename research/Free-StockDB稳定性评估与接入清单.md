# Free-StockDB（fsdb）稳定性评估与可接入数据清单

> 调研日期：2026-09-11 | 执行：实测压测 + 镜像盘点
> 结论先行的版本见 `reports/fsdb稳定性与接入评估.html`

---

## 0. 一句话结论

**fsdb 可以作为现有取数路线的兜底冗余源接入，但不能"裸用"。**
健康态下它是**极快且 100% 可靠**的本地引擎（日线 p50 **29ms**、分钟单日 p50 **58ms**、20 日分钟 p50 **114ms**）；
但它有**一个会致命的自毁模式**——无界/挂起查询会把延迟抬高 20~30 倍甚至彻底塌陷，且**不会自愈，必须重启**（重启仅 4.6~6s，可完全恢复）。
因此接入的正确形态是：**兜底 + 有界查询 + 延迟看门狗**，而不是当作第二个主源随意调用。

## 1. 稳定性实测

### 1.1 三层状态（同一日、同一机、同一数据）

| 状态 | 触发条件 | 日线 p50 | 成功率 | 说明 |
|---|---|---|---|---|
| **健康态** | 服务重启后 | **29 ms**（p95 37ms） | 100% | 24 次串行日线；分钟单日 58ms；20 日分钟 114ms |
| **劣化态** | 发过无界/挂起查询 | **318~686 ms** | ~100% | 延迟放大 11~24 倍，静默 70s **不自愈** |
| **塌陷态** | 持续无界查询 ~27 分钟 | **19,056 ms**（撞 20s 超时） | **16.7%** | 日线 p95 20.8s；分钟线 **8/8 全部超时** |

### 1.2 触发因素隔离实验

逐一排除，得到**唯一元凶是无界查询**：

| 实验 | 结果 | 结论 |
|---|---|---|
| 并发 4 线程 × 6 次日线 | 100% 成功，p50 **39ms**，墙钟 0.2s | ❌ 并发**不是**元凶 |
| 并发 4 线程 × 3 次分钟线 | 100% 成功，p50 81ms | ❌ 并发不是元凶 |
| 通配表名 `板块*` + 有界范围 | 31ms 返回 802KB | ✅ 通配表名本身安全 |
| 通配表名 + **无界范围** `fwz:0,99999999` | 31ms（该表恰好不慢） | — |
| `cmd=keys&t=*` 单发 | **12s 超时** | ⚠️ 无界枚举会挂死 |
| **并发 4 个 `cmd=keys&t=*`** | 4 个全部 60s 超时；**结束后正常查询从 18ms 变成 376~686ms** | ✅ **确认元凶：挂起请求堆积** |

**机制**：引擎对请求没有并发保护，多个无界请求会占满处理槽；请求虽在客户端超时，但引擎侧的作业仍在排队/回收，把正常查询一起拖慢。请求越堆越多、时间越长，最终进入"所有请求都撞超时"的塌陷态（实测 27 分钟压测后成功率 16.7%）。

### 1.3 恢复能力（MTTR）

| 手段 | 效果 |
|---|---|
| 静默等待 30s + 70s | ❌ 仍 318~574ms，**不自愈** |
| **停服 + 重启** | ✅ **4.6~6.0s**，恢复后 13~40ms（提升 ~1000 倍） |

`fsdb_source.stop_service()` / `start_service()` 已实现且实测可用（stop 2.5s、start 3.1s）。

### 1.4 同步链路稳定性

本项目 `fsdb_sync` 域近 3 次运行记录：

| 时间 | 耗时 | 数据量 | 结果 | 数据新鲜度 |
|---|---|---|---|---|
| 2026-09-10 10:29 | 335.6s | 23,988 MB | ok | 20260909 |
| 2026-09-10 22:37 | 336.6s | 23,811 MB | ok | 20260910 |
| 2026-09-11 07:02 | 334.6s | 23,811 MB | ok | 20260910 |

**可用的部分**：3/3 成功，耗时稳定在 334~337s，增量同步 + 断点续传可用，未出现失败。

**必须知道的两个坑**：

1. **无法判定"完成"**：3 次全部触发 `空闲 240s 无进展` 看门狗。同步器（GUI 程序）做完工作后不退出，**"完成"与"网络停滞"在外部观测上无法区分**，只能靠 `.part` 残留数间接判断。
2. **主库已停更**：`data/disable` 内容为
   `Initial synchronization completed. Delete this file to allow this directory to sync again.`
   → 22GB 主库（666 个 `.ldb`，全部为 2026-09-06）**已停止同步**，每日增量全部落在 `data1/`（文件日期 09-06/07/09/10/11 连续）。
   `_part_files()` 同时检查 data 与 data1 是正确的，但**没有任何环节会检测/清理 disable、也没有报警**。
3. **当前有残留**：`data1/` 存在 2 个未完成文件（`003351.log.part`、`MANIFEST-003350.part`，2026-09-11 14:55）→ 上一次增量同步未收尾，需在下一次同步前清理。

### 1.5 其它工程观测

- 引擎进程 RSS **12~14 GB**（`leveldb.cache_size: 500` 配置之外的进程占用），长跑需盯内存。
- 引擎 `log.txt` 出现过多达 **4460s** 的 `long loop time` 历史告警（09-10 22:27），说明服务端主循环历史上被长时间阻塞过；本次压测期间主循环日志反而正常（<1.4s），**瓶颈在查询/响应层而非主循环**。
- 已有防护（保留）：`http_get` 绕过 `HTTP(S)_PROXY` 直连本机、每行 `code` 身份校验（防 pyd 串位）。
- 缺失防护：分级超时、重试、并发闸门、延迟看门狗、disable 检测。

## 2. 稳定性评级与接入姿态

**评级：B（可用，但需护栏）**

| 维度 | 评价 |
|---|---|
| 查询性能（健康态） | ★★★★★ 亚百毫秒，本地无网络成本 |
| 查询可靠性（健康态） | ★★★★★ 实测 100% 成功 |
| 抗滥用能力 | ★☆☆☆☆ 无界查询可致自毁且不自愈 |
| 同步链路 | ★★★★☆ 稳定成功，但完成判定困难 |
| 可运维性 | ★★★☆☆ 重启即愈（5s），但需自建看门狗 |
| 数据新鲜度 | ★★★★☆ T-1（盘前运行语义下正确） |

**四条硬约束（接入时必须内建）**

1. **查询必须有界**：只允许 `t=日k|分钟k|复权|板块*` + `k1=key:<6位代码>` + `k2=fwz:<起>,<止>`
   禁用：`cmd=keys&t=*`、`t=日*`/`t=分钟*`、`fwz:0,99999999`、任何无 `k1` 的全表扫描
2. **并发闸门**：全局串行或 ≤4 线程；禁止把 fsdb 放进无限线程池
3. **超时 + 重试**：单请求 15~20s 超时，失败重试 2 次（退避 1s/3s）
4. **延迟看门狗**：连续 3 次探测 p50 > 500ms 或 10 次采样失败率 > 20% → `stop_service()+start_service()` 自愈（MTTR ≈ 5s）

## 3. 可接入数据类别清单

### 3.1 已核对：镜像实际有什么

| 表 / 接口 | 实测内容 | 规模 |
|---|---|---|
| `日k` | **21 字段**：date/code/name/open/high/low/close/pre_close/volume/amount/turnover/pct_chg/amplitude/is_st/vol_ratio/total_share/float_share/total_mv/float_mv/pe_ttm/pb | 全市场 |
| `分钟k` | 1 分钟 K（code + 14 位时间戳键），open/close/high/low/volume/amount | 2025-01-02 起，5.19 亿行 |
| `复权` | 单股除权事件：div/give/trans/**mult**/**cum** | 600519 共 31 条，2002-07→2026-06 |
| `复权*` | **全市场复权因子总表** | **5,827 只 × 58,654 条，1991~2026** |
| `板块*` | **1,337 个板块 + 成分股名单**：概念 978（同花顺）+ 申万一级 28 / 二级 104 / 三级 227 | 成分中位 18 只，最大 3,835 |
| `股票代码` | 证券宇宙 6 组共 **7,563 只**：0(1493) / 1(995 基金) / 3(1397) / 5(1058 基金) / 6(2311) / 9(309 北交所) | — |

**镜像里明确没有的**（勿再尝试）：`5/15/30/60分钟k`、`tick`/`逐笔`（表名存在但返回 0 行）、**指数行情**（000300/399006 无数据；000001/000905/000852 命中的是同代码个股）、**交易日历**、周线/月线独立表、财务/资金流/两融/龙虎榜/解禁等本地表。

## 4. 建议的接入路线（待确认后执行）

### P0 — 稳定性加固（约半天）
- 在 `fsdb_source.py` 增加：分级超时（默认 15s）、重试 2 次、全局并发信号量（≤4）
- 新增 `health_check()`：小样本探测 p50，超阈值自动 `stop_service()+start_service()` 并记日志
- 新增同步前检查：`data/disable` / `data1/disable` 存在性告警 + `.part` 残留清理
- 明确禁止无界查询（`cmd=keys&t=*` 等），写进模块 docstring

### P1 — 日线/快照自动兜底（约 1 天）
- 把 `backfill_fsdb_daily.py` 的逻辑抽成 `quantlab/data/sources/fsdb_fallback.py`
- 在 `update.py` 的 `kline_daily` / `daily_snapshot` 域内建"主源失败 → 自动切 fsdb → 记录降级标记"
- 保留 `index_kline → 新浪`、`calendar → 新浪` 现有路径
- 目标：把 09-11 那次"三个域 FAIL、需人工跑脚本"变成"三域自动降级、流水线 17/17 成功"

### P2 — 新数据类别入湖（1~2 天）
- 板块映射：`data/lake/clean/board/`，逐日快照累积（解决 PIT 问题）
- 复权因子：与 `dividend_events` 对账报告 → 通过后作为第二源
- ETF 日线/分钟：与 `kline_daily`/`kline_1min` 同构分区入湖
